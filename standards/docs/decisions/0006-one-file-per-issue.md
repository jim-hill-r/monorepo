# 0006. One file per issue

- Status: Accepted
- Date: 2026-11-26
- Decided by: Jim (asked for it; layout chosen by the implementing agent)
- Supersedes: the "one file" part of [0002](0002-human-issues.md); the
  weekly digest and the `needs-human` label stay.
- Amended: 2026-11-28 by Jim, who moved every issue into its project's
  `docs/issues/` (see "Amendment: issues live in each project").

## Context

Work was tracked as list lines in `ISSUES.md` files (40 of them) and tasks
for a person in the root `HUMAN_ISSUES.md`. Many agent threads now work in
parallel, and most of their PRs add or remove a line in the same few files
(the root `ISSUES.md`, `pane/ISSUES.md`, `HUMAN_ISSUES.md`). Every merge then
put the others in conflict, and each conflict cost an agent run to resolve.
Jim asked for each issue to be its own file in a directory (2026-11-26).

Options considered:

- **`merge=union` in `.gitattributes`** for the issue files. No format
  change, but it only helps where git itself merges. We could not confirm
  that GitHub's server-side merge (PR mergeability, the merge button,
  auto-merge) honours it, so PRs could still show as conflicting. It also
  keeps both sides blindly, which can bring back a line one side deleted.
- **One file per issue, numbered** (`0042-...md`). Two parallel PRs would
  pick the same next number.
- **One file per issue, named by a slug, with front matter.** Adding and
  closing issues never touch a shared file.

## Decision

- Every issue is one Markdown file with front matter (`kind`, `priority`,
  `added`, and optional `tags`, `epic`, `order`), named by a slug, in the
  `docs/issues/` folder of the project it belongs to:
  `<project>/docs/issues/<slug>.md`, and
  `<project>/docs/issues/human/<slug>.md` for tasks only a person can do.
  Repo-wide work goes in the platform project that owns it, and in
  `standards/docs/issues/` when no other fits. There is no root `issues/`
  folder. The format is in [issue-management.md](../issue-management.md).
- Prose that isn't one issue (epic notes) goes in the folder's `README.md`.
  The priority and on-hold project lists live in
  [`standards/docs/issues/README.md`](../issues/README.md).
- The list is generated by `mise run //:issues` (`standards/scripts/issues.sh`)
  and never committed. The audit checks the files (ISS-001 to ISS-004),
  replacing HUM-001; ISS-001 also fails an issue file left in a root
  `issues/` or `<project>/issues/` folder.
- The 201 existing issues and 9 human tasks were moved by a one-off script
  that kept their text, section, epic, order and tags, and took each one's
  `added` date from `git blame`.

## Consequences

- Parallel PRs that add or close different issues no longer conflict. Two
  PRs editing the same issue still do, as they should.
- Ordering inside an epic is the `order` field instead of line order, and
  an epic's notes sit apart from its issues in `README.md`.
- Reading every issue now means running the list command (or pane) instead
  of opening one file.
- Pane's snapshot, the audit, and the `start-a-new-task`, `code-review`,
  `human-issues-digest`, `deep-project-review` and `open-pull-request`
  skills read the new layout.
- Open PRs that edited an old file get a modify/delete conflict once this
  merges; they resolve it by turning their lines into issue files (see
  issue-management.md).

## Amendment: issues live in each project (2026-11-28)

Jim (2026-11-28): "I noticed the top level issues directory has a ton of
issues in it. Issues should live in the docs/issues directory in a given
project. Pane should aggregate human issues from all the projects."

The first layout had a root `issues/` for repo-wide work (111 issues by
then), a root `issues/human/` for every human task, and `<project>/issues/`
beside each project's code. That made the root folder a dumping ground
whose issues no project owned, and a project couldn't be moved out with
its own backlog.

- Every issue moved, unchanged apart from its links, into
  `<project>/docs/issues/` (and `docs/issues/human/`): by epic, so the
  eval engine went to `evals`, IaC and infra fixes to `infra`, threat check
  to `threat`, cost tracking, cost check and revenue to `cost`, and a
  project-specific issue (an advisory, a smoke test) to that project.
  Repo-wide work with no other owner (code quality, review roles, resource
  cleanup, user feedback, free tiers, CI and UAT tasks) went to
  `standards`, which also holds the priority and on-hold lists.
- Each project's own `issues/` folder moved to `docs/issues/`.
- `chores next-task` no longer has a "root issues first" group: the order
  is the priority projects' `priority` issues, then every other `priority`
  issue, then backlog. `standards` issues are keyed by epic, as root issues
  were, so several threads can work it at once.
- `chores new-human-task` takes `--folder` (default `standards`), and
  `evals human-checks` writes settings checks to
  `standards/docs/issues/human/`.
- Pane reads human tasks from every project's `docs/issues/human/`, shows
  each one's project, and counts a project's own human tasks in its Open
  issues signal.
