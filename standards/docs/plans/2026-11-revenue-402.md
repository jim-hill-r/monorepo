## Summary

A note on words: the **financial ledger** is the project's accounting
books, the record of every dollar in and out, kept as files in this public
repo. The **public ledger page** is a web view of it.

- **HTTP 402 is real now, and Cloudflare is in the middle of it.** The
  x402 protocol (created by Coinbase, now run by the x402 Foundation, which
  Coinbase and Cloudflare founded) is on version 2, and Cloudflare ships
  open Worker middleware for it. Its managed product, **Monetization
  Gateway**, needs a credit card on file and a domain on Cloudflare, so it
  breaks our "no payment method" rule today.
- **We can take 402 payments on the free plan without Cloudflare's managed
  product**: our own Workers return 402 and hand verification to a
  facilitator. The Coinbase facilitator settles 1,000 payments a month for
  free, then $0.001 each, and pays the gas. Money lands as USDC in a wallet
  address only Jim controls. That needs a new vendor (Coinbase Developer
  Platform), so it needs Jim's sign-off.
- **Honestly, 402 revenue will be near $0 for a long time.** Real x402
  commerce across the whole internet was about $25 million by September 2026,
  mostly a few thousand bot wallets, and we have no API that outsiders want
  yet. Donations are the realistic money. So the plan puts **a public financial
  ledger and GitHub Sponsors first** (both $0, GitHub is already approved) and makes
  402 a staged experiment.
- **"Our own apps pay like any customer" is done by shadow billing, not by
  moving real money.** Paying ourselves on-chain would cost fees, mean a
  wallet key inside every browser and CLI (a secret we can't protect), and
  move money from one of Jim's pockets to another. Instead every API meters
  every call at its list price, and first-party use is charged against the
  ledger at that price, visibly, without a wallet.
- **Stopping the apps saves nothing.** Every app runs on free tiers, so
  money only goes to Claude Code ($25 a month). The cutoff is a call for
  support, not a cost control. The lever that actually protects cash is
  pausing agent work, so the plan proposes both, and asks Jim how hard the
  app cutoff should be.

## Long-term vision

Jim expects APIs soon, so this plan is the money model for the whole repo,
not a one-off experiment. Where it ends up:

| Stream | What it is | Rail | From |
| --- | --- | --- | --- |
| **Sponsorships** | People and companies who want the projects to exist | GitHub Sponsors | Phase 2 |
| **API sales** | Agents and developers paying per call above a free allowance | x402 (HTTP 402, USDC), MPP later if card payers appear | Phase 4 (testnet), phase 5 (real money) |
| **Royalties** | Production users of our libraries paying what their `royalty.toml` terms ask | Whatever royalty's report names: GitHub Sponsors and invoices first, x402 later | Phase 3, then royalty's own phases |
| **Owner contributions** | Jim paying what nothing else covers | Recorded, not collected | Phase 1 |

Three rules make it last as APIs arrive:

1. **Every new API is born metered and 402-ready.** From phase 3 on, a new
   API uses the `meter` crate and declares `[[price]]` in its
   `docs/cost.toml` on its first PR, even if every price is $0 and its free
   allowance covers everyone. Turning on payment later is then a price
   change, not a rewrite.
2. **One ledger for every stream.** Each `[[revenue]]` entry's `source`
   starts with its stream (`sponsors:`, `x402:`, `royalty:`, `gift:`,
   `owner:`), so the ledger, the runway and pane split income by stream
   without a new file.
3. **One 402 for everything.** "Pay for this call", "royalty due" and
   "we're out of money" all answer HTTP 402 with the same JSON shape and,
   from phase 5, the same x402 header. The `pay402` crate is shared by our
   APIs and royalty.

## Royalty income

The [royalty project](../../../royalty/README.md) lets a library's author
put payment terms in a `royalty.toml`: free for development, tests and CI,
paid in production up to caps, and a ceiling on what anyone pays. This repo
is both a **producer** and a **consumer**, and both sides go in the ledger.

- **Income:** our own reusable code (`auth_sdk`, `design_system`, royalty's
  own crates, and any library or framework we publish later) can carry a
  `royalty.toml` naming Jim as payee. Royalty's MVP is a report the
  consumer pays by hand, so income arrives through GitHub Sponsors or an
  invoice and is recorded as `[[revenue]]` with `source = "royalty:<payer>"`.
  The default stays generous (free below production and below a small
  ceiling), since adoption matters more than money early on; the terms are
  Jim's call per library.
- **Costs:** when our projects depend on someone else's library with
  royalty terms, `royalty check` reports what we'd owe. Royalty's budget
  gate holds our consumer budget at $0 until Jim sets one, so a dependency
  can never start a bill on its own. A budget above $0 is a `[[cost]]` with
  a decision record, like any other money.
- **Dogfooding:** the money run counts royalty income and owed royalties
  the same way as sponsors and API sales, and the public ledger page shows
  them, which makes this repo royalty's first real example.
- **Other royalties** (a book from a writing project, a game on a store)
  are recorded the same way, `source = "royalty:<where>"`, by Jim through
  the pane form.
- **Tax:** royalty income is ordinary income like the rest; whether it is
  business or royalty income on Jim's return is for the tax professional
  (see [Tax and legal](#tax-and-legal-not-advice-jim-should-check-with-a-tax-professional)).

## Research

Everything below was checked on 2026-11-27 against the sources linked in
[Sources](#sources). Where only a secondary source gave a number, it says so.

### HTTP 402 protocols

| Protocol | Who | How it works | State |
| --- | --- | --- | --- |
| **x402** | Created by Coinbase; x402 Foundation (Coinbase and Cloudflare are founding members) | Server answers `402` with a `PAYMENT-REQUIRED` header (base64 JSON: price, network, asset, `payTo` address). Client signs a stablecoin transfer authorization and retries with `PAYMENT-SIGNATURE`. A **facilitator** verifies and settles on-chain and the server returns `PAYMENT-RESPONSE`. Schemes: `exact` (fixed price) and `upto` (authorize a maximum, settle the actual). | Version 2. Networks include Base, Ethereum, Polygon, Arbitrum, Solana and others; USDC is the usual asset. |
| **MPP** (Machine Payments Protocol) | Tempo and Stripe, announced 2026-03-18 | `WWW-Authenticate: Payment` challenge, `Authorization: Payment` credential, `Payment-Receipt`. Payment methods include cards (Stripe, Visa), stablecoins (Tempo, USDC), Lightning. Has **sessions** (a prepaid channel with off-chain vouchers per request), so sub-cent prices don't each pay a fee. | An individual IETF Internet-Draft, not a standard. Compatible with x402 `exact` flows. Card payments need the seller to have a Stripe account. |
| **Pay per crawl** | Cloudflare | `402` with a `crawler-price` header for AI crawlers only. Cloudflare is merchant of record and pays out through Stripe. | Closed beta, needs a Cloudflare zone. Only charges verified AI crawlers. |

### What Cloudflare offers

| Offering | Fits our rules? | Why |
| --- | --- | --- |
| **Agents SDK x402 support**: `x402-hono` middleware for Workers, `withX402` and `paidTool` for MCP servers, `withX402Client` for paying | **Yes**, it is open code that runs on Workers Free | It is TypeScript; our Workers are Rust (below). Needs a facilitator. |
| **x402-proxy** and **mpp-proxy** Worker templates | **Yes**, same as above | A Worker in front of any backend that charges listed routes. Optional Bot Management selective gating is a paid feature we can't use. |
| **Monetization Gateway** (managed x402, closed beta since 2026-09-30) | **No, not today** | Seller must keep a **credit card on file** (our rule 1: never add a payment method), have an account older than 60 days, and a **zone** proxied by Cloudflare for 30 days (we have no domain on Cloudflare; a domain costs money). Buyers and sellers must be in the US. It settles through the Coinbase facilitator anyway. |
| **Pay per crawl** | **No** | Closed beta, needs a zone, and charges only AI crawlers, not API users. |
| **AI Gateway Machine Payments** | Not relevant | That is Cloudflare *selling* inference by x402; it also needs a card on file. |

So the part of Cloudflare's tooling that fits the free plan is the open
middleware, not the managed products. If Monetization Gateway later drops
the card requirement and we have a domain, it would replace phase 5's
facilitator code; the meter and ledger stay the same.

### Settlement rails

| Rail | What we'd need | Fees | Fits? |
| --- | --- | --- | --- |
| **Coinbase CDP facilitator** (x402, mainnet) | A CDP account and API key (key id and secret) on the Worker. A public `payTo` address. No wallet private key on the server. | First 1,000 settlements a month free, then $0.001 each. Verify is free; failed settles aren't billed. Facilitator pays gas. Every payment is screened for sanctions (KYT/OFAC). | **Yes with sign-off**: a new vendor at $0 inside 1,000 payments a month. The fee is charged to a CDP account, so we must confirm the free tier needs **no card on file**; if it does, the rail is out. |
| **x402.org facilitator** | Nothing | Free | **Testnet only** ("not intended for mainnet routes"). Good for the pilot. |
| **Self-hosted facilitator** (e.g. `x402-rs`, Apache-2.0) | A server, an RPC endpoint, and a **hot wallet private key with ETH for gas** | Gas on every settlement | **No**: it spends money on gas and keeps a spendable key in a running service. |
| **Other facilitators** (PayAI, thirdweb 0.3%, Dexter, AsterPay) | Vendor accounts | Percentage fees, per vendor pages | Worse than CDP on cost, more vendors. |
| **MPP with Stripe** (cards) | A Stripe account with identity and bank details | Card fees (not published for MPP; standard Stripe card pricing is far above a micropayment) | **No for now**: new vendor, and card fees make per-request prices pointless without sessions. Revisit if people want to pay by card. |
| **MPP on Tempo** (stablecoin sessions) | A Tempo wallet, another chain | Network fees | Later, if sub-cent prices matter. Same wallet questions as x402. |

**Holding the money with no payment method.** Receiving money isn't a
payment method on a vendor. x402 payments go straight on-chain to a
`payTo` address; CDP never holds revenue. The address is public and is the
only thing the Worker knows. Its private key stays with Jim (a hardware
wallet or his own Coinbase account) and never touches git, OpenTofu state,
a GitHub secret or a Worker. Turning USDC into dollars is Jim's own step in
his own exchange account (identity checks and exchange fees apply there).
GitHub Sponsors pays into Jim's bank account through Stripe Connect; that
is a payout account, not a payment method on GitHub.

**Rust.** Our Workers are Rust (`workers-rs`). The `x402-rs` crate (0.12.5,
January 2026, Apache-2.0) supports v2 and has an axum seller middleware,
but pulls in tokio and the Solana client, so it almost certainly won't
build for wasm32. The protocol is small: base64 JSON in headers plus two
HTTPS calls to the facilitator (`verify`, `settle`). The plan writes a thin
`pay402` crate on `serde` and the Worker `fetch`, with the header types
tested against the published v2 examples, instead of depending on a crate.

### What the ecosystem really looks like

From TRM Labs and Visa figures (via a secondary source, October 2026): about
199 million x402 settlements worth about $53 million by September 2026, of
which about $26 million looked like real commerce; about 4,000 wallets made
about 90% of spending; one study found 21% of Base settlements fictitious.
A USENIX Security 2026 paper tested 15 facilitators and found 31 new
vulnerabilities (free shopping, asset theft, service denial, gas abuse);
Coinbase adopted fixes. x402 has no refunds or disputes built in, and
payments can't be charged back.

The takeaway: 402 is promising for agents paying for data and tools, but
it is small, young and mostly machine-to-machine. People in a browser don't
have USDC wallets. Plan for donations to carry the accounts and treat 402 as
an experiment that costs us nothing to keep.

### Tax and legal (not advice; Jim should check with a tax professional)

- **Everything received is taxable income**, form or no form. GitHub sends a
  1099-NEC above the yearly threshold (raised for 2026, see
  [0016](../decisions/0016-holding-and-handling-money.md)); payment platforms send a 1099-K only above
  $20,000 and 200 transactions (restored by the One Big Beautiful Bill).
  Digital assets must be reported whether or not a 1099-DA arrives.
- **USDC received for a service** is ordinary income at its dollar value on
  the day it arrives (IRS property treatment, Notice 2014-21, per secondary
  sources); selling it later is a disposal, normally with no gain since it
  stays at $1. Many tiny payments mean many records, so the ledger must
  keep each settlement's date, amount and transaction hash.
- **Business or hobby.** Run as a business (Schedule C), costs such as
  Claude Code are deductible and net profit over $400 pays 15.3%
  self-employment tax. As a hobby, income is taxed with no deductions.
  Which applies is a question for a professional, and it decides whether
  "Claude Code minus sponsorships" is a real number on Jim's return.
- **Donations to Jim aren't tax-deductible** for the giver. The splash page
  must say so and must not call itself a charity.
- **Sales tax.** Selling API access is a taxable digital service in some
  states, and some states count transactions (as low as 200) toward a
  seller's obligation, which micropayments could reach fast. A merchant of
  record (Polar, or Cloudflare when its products fit) would carry this;
  direct x402 sales leave it with Jim. This is the main legal reason
  phase 5 waits for real demand and a professional's view.
- **Not a money transmitter, if we keep it that way.** Selling our own
  services is fine. Holding other people's refundable prepaid balances,
  or issuing tokens or credits that can be cashed out, starts to look like
  stored value; the plan never does either.
- **Paperwork before taking money:** terms of service, a privacy note and a
  refund policy for any paid API, and the GitHub Sponsors terms for tiers.
- **Superseded by [decision 0016](../decisions/0016-holding-and-handling-money.md)**
  (where money is held, the accounting rules, card payments): a separate
  free account with an EIN before Sponsors, and an LLC later. The original
  note follows.
- **Possible later step:** a single-member LLC and a separate bank account,
  to keep project money apart from Jim's own. Only worth it once revenue is
  real; it costs state fees, so it is Jim's decision.

## Recommended architecture (E)

```text
                ┌────────────── public repo (the ledger) ─────────────┐
                │ <project>/docs/cost.toml   [[cost]] [[revenue]]       │
                │ standards/money/statements/<yyyy-mm>.json  (monthly)  │
                └───────────────▲──────────────────────────▲───────────┘
                                │ monthly PR               │ read
   GitHub Sponsors ─┐   ┌───────┴────────┐          ┌──────┴───────┐
   (Sponsors API)   ├──►│ money workflow │─────────►│ pane Worker  │──► /open (public):
   CDP settlements ─┤   │ daily, Actions │ runway   │  money model │    revenue, cost,
   (Worker log)     │   └───────▲────────┘ .json    └──────┬───────┘    runway, usage
   Billing checks ──┘           │                          │ GET /api/runway (CORS)
                                │ usage                    ▼
                    ┌───────────┴──────────┐    every app and CLI: banner, splash
                    │ Analytics Engine     │◄── every API call: meter(project,
                    │ `meter` dataset      │    route, caller, list price)
                    └──────────────────────┘
```

### 1. The financial ledger

- **Money in** is `[[revenue]]` entries: GitHub Sponsors payouts, x402
  settlements (summed per month, with a link to the settlement log),
  and any other gift. Jim's own spending on the project, if he chooses, is
  an **owner contribution**, shown as such, never disguised as revenue.
- **Money out** is every `[[cost]]` entry plus the radar's shared budgets,
  today only Claude Code at $25 a month. Actuals come from the billing
  checks and Jim's settings checks (PR #760, PR #756).
- **Statements.** A monthly workflow writes
  `standards/money/statements/<yyyy-mm>.json` (opening balance, each line
  with its source, closing balance) and opens a PR, which PR triage merges
  like a `pane-edit` PR when only revenue and $0 costs changed. Git history
  is the audit trail and the repo is public, so the ledger is public by
  default.

### 2. Free cash flow and runway

- `balance = opening balance + Σ(revenue + owner contributions − costs)`
  over every month since the start date Jim picks.
- `burn` = the average net cost of the last three months.
- `runway_months = balance / burn` (infinite when burn ≤ 0).
- **Status**: `funded` (runway of 3 months or more), `low` (under 3
  months), `out` (balance below zero). The thresholds are in one TOML file
  so Jim can change them in a PR.
- The daily money run (it joins the daily usage workflow from cost tracking
  phase 1) computes this and writes `runway.json`. pane serves it at
  `/api/runway`, public and cached, and apps read it from there.

Today's numbers make the choice concrete: revenue $0, cost $25 a month.
Without an opening balance or owner contributions, status is `out` on day
one. That is why decision 2 below is the most important one.

### 3. Metering and shadow billing ("our apps pay like anyone else")

- A shared Rust crate, `standards/crates/meter` (or inside `pane/model` if
  only Workers use it), gives each Worker one call per request:
  `meter(project, route, caller, list_price_micro_usd)`, written to an
  Analytics Engine `meter` dataset (free: 100,000 writes a day, shared with
  telemetry).
- `caller` is `first_party` (our own UI or CLI, recognised by origin or a
  build-time client id, which is **not** a secret and not trusted for
  anything but labelling), `third_party`, or `paid` (a settled x402
  payment).
- Each API publishes its price list in its `docs/cost.toml` (new
  `[[price]]` table: route, micro-dollars per call, free allowance).
- Each month the money run turns first-party calls into an **internal
  charge** on the statement: "cookbook UI used 41,000 recipe calls at
  $0.0001 = $4.10". No money moves; the line nets to zero between the app
  and the API, but users can see what our own apps would pay.
- Third-party calls inside a free allowance are metered but free. Above
  it they get `402` (phase 4 on).

### 4. The 402 path (phases 4 and 5)

- A small `pay402` crate (Rust, `serde`, Worker `fetch`) builds the x402 v2
  `PAYMENT-REQUIRED` header, forwards `PAYMENT-SIGNATURE` to the
  facilitator's `verify`, does the work, calls `settle`, and returns
  `PAYMENT-RESPONSE`. It never holds a key that can move money.
- **Order of operations:** verify, then do cheap work, then settle, then
  return. Expensive work only after settle. On `settlement_pending`,
  reconcile by transaction hash; never retry blindly (CDP double-charge
  warning).
- **Prices** start at the CDP minimum economics: no price below $0.001
  (also Cloudflare's minimum), so the facilitator's $0.001 above the free
  tier can never exceed revenue.
- **Free-tier guard:** the Worker counts settlements this month; at 900 of
  1,000 it stops offering x402 and returns the donation response until the
  1st. That is the "stop, don't pay" rule.
- **Same 402 for "out of money".** When status is `out`, an API returns
  `402` with a JSON body linking the Sponsors page (and, from phase 5, a
  `PAYMENT-REQUIRED` header so an agent can pay to continue). One status
  code, one meaning: payment required.

### 5. Donations, the banner and the cutoff

- **Funded**: a small "Supported by sponsors, see our finances" link in each
  app's footer.
- **Low**: a dismissable banner: "This project has N months of runway.
  Sponsor on GitHub." with a link to the public ledger.
- **Out**: the splash page. It explains the numbers in one line, links
  GitHub Sponsors, says gifts aren't tax-deductible, links the public ledger, and
  (if Jim picks the soft cutoff) offers "continue anyway". A shared Dioxus
  component in `design_system` so every app shows the same thing.
- **CLIs** read `/api/runway` at most once a day and print one line on
  stderr; with a hard cutoff they exit with a message and code 75
  (`EX_TEMPFAIL`).
- **What stops for real:** the only thing that spends money is agent work.
  When status is `out`, the coordinator starts no new threads except
  security fixes and PR triage, the same rule as Claude overage (PR #756).
  That is the change that actually protects cash.
- **Never cut off:** `infra`, `tofu_state`, Infra Mint, security fixes,
  telemetry (it records the cutoff itself), and the public ledger page.
- **Free-tier exhaustion** (Workers 100,000 requests a day, error 1027) gets
  its own message on the same component: "We hit today's free limit, back
  at 00:00 UTC; sponsors help us stay free." It isn't the same as `out`.
- Static sites can't truly be stopped (the page is already in the
  browser), and they shouldn't be. The splash is a request, not DRM.

### 6. Transparency for users

- The repo is public, so the statements and `cost.toml` files are the
  primary record, and every number links to its line.
- A **public ledger page** shows this month's revenue, each cost,
  runway, each app's internal charge and free-tier headroom. Two places it
  could live (decision 6): a public `/open` path on the pane Worker (pane is
  otherwise behind Cloudflare Access, so this is an Access bypass rule, a
  credential change), or a static page on a public site we already deploy.
- Private sponsors stay private: the page shows their amounts as
  "anonymous", never names, matching GitHub's own visibility setting.

### Abuse and fraud

| Threat | Control |
| --- | --- |
| Flooding the 402 path to burn the shared 100,000 requests a day | Per-IP rate limit (the telemetry pattern), cheap 402 responses with no work, and the daily-limit message. |
| Getting work without paying (verify passes, settle fails) | Settle before expensive work and before returning paid data. |
| Double charges on retries | Idempotency by payment nonce; reconcile `settlement_pending` by transaction hash. |
| Facilitator bugs (USENIX 2026) | Only the CDP facilitator, pinned API version, settlement amounts reconciled daily against the wallet balance read from a public RPC. |
| Fake "first party" callers | The label only affects reporting, never price or access; first-party traffic gets no free pass beyond the public free allowance. |
| Sanctioned payers | CDP screens every payment (KYT/OFAC); declined ones fail. |
| Stolen-card donations | Handled by GitHub and Stripe; we never touch card data. |
| Fake volume to look popular | Statements count settled dollars, not call counts. |
| Refund demands | x402 can't be charged back. A refund policy in the terms; refunds are a manual transfer from Jim's wallet, recorded as negative revenue. |
| Wallet theft | The key is never online in our systems; the Worker knows only the address. Rotating the address is a config change. |

## Phases

Each phase is one issue file (`epic: Revenue`), except phases 4 and 5,
whose issues are added when Jim approves them. Claude Code effort counts
against the $25 a month budget, so the phases are backlog work.

### Phase 1: the financial ledger and runway ($0, no vendor, about 1 session)

- `standards/money/` with `runway.toml` (start month, opening balance,
  thresholds) and a `money` model in `cost/model`: balance, burn, runway,
  status, with unit tests for each edge (no revenue, negative balance,
  zero burn).
- `cost money` CLI command writes `runway.json` and the monthly statement;
  the daily usage workflow runs it and uploads the JSON.
- `standards/docs/money.md` describes the files.

### Phase 2: GitHub Sponsors, the banner and the splash ($0, GitHub, about 1 to 2 sessions)

- Jim sets up GitHub Sponsors on his personal account (human issue and
  runbook: 2FA, Stripe Connect bank account, W-9, tiers). About 20 minutes.
- Sponsors totals read by the money run. Reading your own sponsorships
  needs a token of the sponsored account, so either a fine-grained token
  of Jim's in `infra-credentials` (credential change) or Jim adds the
  monthly payout by hand through a pane form (decision 5).
- pane serves `/api/runway`; a shared `Runway` banner and splash component
  in `design_system`; the apps and CLIs adopt it; the coordinator's
  "out means no new threads" rule goes into AGENTS.md.

### Phase 3: meter and shadow billing ($0, no vendor, about 1 session)

- The `meter` crate and Analytics Engine dataset, `[[price]]` tables in
  `docs/cost.toml` (checked by `cost check`), internal charges on the
  statement, and the public ledger page.

### Phase 3b: royalty income ($0, no vendor, about 1 session)

- After royalty's Phase 1 (`royalty check`, `scan`, `report`): add a
  `royalty.toml` to our reusable libraries with terms Jim approves, run
  `royalty check` on our own projects in the money run, record owed
  royalties (held at $0 by the budget gate) and royalty income in the
  statements, and show both on the public ledger page.

### Phase 4: x402 pilot on testnet ($0, ask Jim, about 2 sessions)

- The `pay402` crate and one paid route (bear_down or cookbook) on Base
  Sepolia with the x402.org facilitator and free test USDC. Proves the
  flow end to end, including an MCP `paidTool`-style tool, with Playwright
  and integration tests. No real money, no secrets.

### Phase 5: x402 on mainnet (gated, about 2 sessions)

Starts only when all of these are true:

1. An API has outside users asking for more than its free allowance. Jim
   expects this soon, so phase 4 targets the first new API that ships
   rather than waiting for a perfect candidate.
2. Jim has approved Coinbase CDP as a vendor in a decision record, and
   confirmed its free tier needs no card on file.
3. Jim has a receiving wallet whose key never enters our systems.
4. Jim has a tax professional's view on income, sales tax and records.
5. The API has terms of service, a privacy note and a refund policy.

Then: the CDP key through `infra-credentials`, a `Coinbase CDP` radar blip
with its 1,000-a-month budget and the 900 stop, a billing-check line, and
the wallet address on the Sponsors page.
