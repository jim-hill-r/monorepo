# infra

[![Eval coverage](https://raw.githubusercontent.com/jimhillr/monorepo/evals-results/badges/infra.svg)](https://github.com/jimhillr/monorepo/blob/evals-results/verdicts.json)

Infrastructure as code for the monorepo: the settings we used to click
through vendor dashboards (Auth0 applications first, then GitHub and
Cloudflare) written as Rust, in the style of the AWS CDK. It is named for
what it holds. The design is [decision 0007](../standards/docs/decisions/0007-infrastructure-as-code.md).

How it works:

1. **Constructs** (`src/constructs.rs`) say what we mean, such as
   `WebApp::new("cookbook").sign_in(Auth0App::import(...))`.
2. **Stacks** (`src/stacks/`) expand them into provider resources, using
   typed bindings generated by [terrars](https://github.com/andrewbaxter/terrars)
   (`src/tfschema/`).
3. **Synth** (`cargo run -- synth`) writes one OpenTofu root module per
   stack, `out/<stack>/main.tf.json`, with sorted keys. That file is
   committed and reviewed; CI fails if it differs from a fresh synth.
4. **OpenTofu** plans and applies `out/<stack>/`. This program never calls a
   vendor API. State is kept, encrypted, by the `jimhillr-tofu-state`
   Worker with D1 through OpenTofu's `http` backend, one URL per stack with
   locking ([decision 0009](../standards/docs/decisions/0009-opentofu-state-http-backend.md));
   it is never committed to git. `infra backend-config <stack> <origin>`
   prints the `tofu init` arguments for a stack.

| Stack | Manages | Credentials |
| --- | --- | --- |
| `auth0` | The cookbook and cahokia Auth0 applications: callback, web origin and logout URLs for production, Pages previews (`https://*.<pages project>.pages.dev`) and localhost, and the Single Page Application type | `AUTH0_DOMAIN`, `AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET` from the environment |
| `cloudflare` | Web Analytics on each production Pages site (`cloudflare_web_analytics_site`, beacon auto-installed); wrangler still creates and deploys the Pages projects | `CLOUDFLARE_API_TOKEN` and `TF_VAR_cloudflare_account_id` from the environment |
| `github` | This repository (imported, with every setting written out), secret scanning and push protection, Dependabot alerts and security updates, and a `CI` ruleset that requires `CI result` from GitHub Actions on `main`. Never the `Default` ruleset (provider 6.13.0 can't express its unattributed-changes rule, so an update would drop it), any bypass list or the `infra-credentials` environment | `GITHUB_TOKEN` from the environment: a token minted per run from the read-only infra GitHub App for plans, and from the infra GitHub App for applies |

Every resource that already exists is brought in with an `import` block, and
every resource has `prevent_destroy`: IaC never deletes anything (decision
0007, item 8).

## Plan guards

`cargo run -- guard plan.json` checks the JSON of a saved plan
(`tofu show -json plan.tfplan > plan.json`) and fails on any finding. The
workflows run it on every plan before it is shown or applied.

| ID | Fails when |
| --- | --- |
| IAC-001 | the plan deletes or replaces anything (forget it with a `removed` block instead, which the guard allows) |
| IAC-002 | any attribute the provider marks sensitive would hold a value in state, whether we set it or the vendor generates it (secrets never go in git or state, even encrypted); write-only attributes pass |
| IAC-003 | a resource type that can bill (R2, subscriptions and the like), or more Pages projects, Workers or Cron Trigger schedules than the budgets in `standards/radar/limits.toml` |
| IAC-004 | a provider or resource type not allowlisted in `src/guard.rs` |
| IAC-005 | the plan changes the `infra-credentials` environment (its reviewers, secrets or deployment policy) or a ruleset's bypass list, which IaC never manages ([decision 0010](../standards/docs/decisions/0010-credential-second-approval.md)) |

The lists live in `src/guard.rs`. Add a resource type to the allowlist in the
PR that first uses it, after checking it can't bill; a test fails if a stack
uses a type that isn't listed. The guards are tested on fixture plans in
`tests/fixtures/plans/`, one of them real OpenTofu output.

### Credential changes

The guard also lists every **credential change** in the plan, without
failing it: a create or update of an Auth0 client grant, resource server,
connection or role, a new Auth0 client, an `auth0_client` change to
anything but its names and URLs, a Cloudflare API token or Access
resource, or anything in the `github` stack. `--report report.json` writes
`{"credential_change": true, "changes": [...]}` for the workflows: a stack
with a credential change applies only in the `infra-credentials` GitHub
environment, after Jim approves that run (decision 0010). The lists are
`CREDENTIAL_TYPE_PREFIXES` and `AUTH0_CLIENT_NOT_CREDENTIAL` in
`src/guard.rs`; the second is a list of what's safe, so a new attribute
counts as a credential until it is added there.

## Workflows

The `github` stack has no everyday apply tier: GitHub can't separate its
settings from rulesets and secrets, so every change it makes is a
credential change (decision 0010) and applies only in `infra-credentials`.
Its plans mint a token from the read-only infra GitHub App
(`GH_INFRA_READ_APP_ID` variable, `GH_INFRA_READ_APP_KEY` repository
secret, [runbook](../standards/docs/runbooks/github-app-infra-read.md)),
and its apply mints one from the infra GitHub App, whose key is only in
`infra-credentials`.

`scripts/tofu.sh` does the work; the workflows only pass it secrets
(tested by `tests/tofu_sh.test.sh` and `jimhillr/workflow_tests`).

| Workflow | When | State password | Vendor credentials | Environment |
| --- | --- | --- | --- | --- |
| `infra-plan.yml` | PRs changing `infra/` | read, `-lock=false` | read | none |
| `infra-apply.yml`, plan | push to `main` | write, locks | read | `infra` |
| `infra-apply.yml`, apply | a stack with changes | write | apply | `infra` |
| `infra-apply.yml`, apply credentials | a stack with a credential change | write | credentials | `infra-credentials` (waits for Jim) |
| `infra-drift.yml` | Mondays | read, `-lock=false` | read | none |

Each plan is written to the job summary with its SHA-256, the guard result
and whether it changes a credential. A PR whose plan changes a credential
gets the `credential-change` label. The apply jobs apply exactly the saved,
encrypted plan after checking its hash; OpenTofu refuses it if state moved
since. The JSON plan is only for the guards and is never uploaded. Every job
that touches state on `main` shares the `infra` concurrency group with the
state Worker's deploy.

A stack whose secrets aren't set yet is skipped with a notice rather than
failed, so the workflows can merge before the setup is done.
`TOFU_STATE_ORIGIN` is a repository variable.

## Minting credentials

OpenTofu never makes a secret: anything a vendor generates would land in
state (IAC-002). The **Infra Mint** workflow (`infra-mint.yml`, run by hand,
in `infra-credentials`, so it waits for Jim's approval) makes them instead.
`scripts/mint.sh` takes each value from the vendor's API response, or from
`openssl rand`, and pipes it into `gh secret set`, masked in the log. It is
never written to git, state or a file, and no one sees it (Jim, 2026-11-27).

| Minted | Where | From |
| --- | --- | --- |
| `TOFU_STATE_READ_PASSWORD`, `TOFU_STATE_PASSPHRASE` | repository secrets | `openssl rand` |
| `TOFU_STATE_WRITE_PASSWORD` | `infra` | `openssl rand` |
| `TOFU_STATE_ORIGIN` | repository variable | the account's workers.dev subdomain |
| `CLOUDFLARE_API_TOKEN` (`jimhillr-deploy`: Pages, Workers Scripts, D1 Write, Account Analytics Read) | repository secret | Cloudflare account-owned token |
| `CLOUDFLARE_INFRA_READ_TOKEN` / `_APPLY_TOKEN` | repository / `infra` | Cloudflare account-owned tokens |
| `CLOUDFLARE_BILLING_READ_TOKEN` (`jimhillr-billing-read`: Billing Read) | `infra` | Cloudflare account-owned token, for the weekly billing check |
| `AUTH0_INFRA_READ_*` / `AUTH0_INFRA_APPLY_*` | repository / `infra` | Auth0 Machine to Machine apps `infra-read` and `infra-apply` |
| `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD` | repository secrets | `keytool`, in the job |

It makes only what is missing, so it is safe to re-run; the `rotate` input
names secrets to remake, and `auto` remakes the quarterly set. A scheduled
run does that on the 1st of January, April, July and October, after Jim
approves it, and minted Cloudflare tokens expire 180 days after each mint
([rotation plan](../standards/docs/secret-rotation.md)). The state passphrase is not rotated this way
yet; see [Rotating the state passphrase](#rotating-the-state-passphrase). When the passwords or the deploy token change, it
queues **Deploy tofu_state**. A person makes only the bootstrap credentials:
`standards/docs/runbooks/infra-credentials-environment.md`. Tested by
`tests/mint_sh.test.sh`.

## Rotating the state passphrase

OpenTofu keeps each key's PBKDF2 salt in the state under the key
provider's name, so a new passphrase needs a new name. The passphrase
therefore has generations: `TOFU_STATE_KEY_GEN` (default 1) names the
current one. Generation 1 is the `state` key in the committed stacks; from
generation 2 on, `scripts/tofu.sh` passes `infra encryption <gen>` in
`TF_ENCRYPTION`, which encrypts under `gen_<n>` and falls back to the
previous generation's key with `TOFU_STATE_PASSPHRASE_OLD`. A no-op apply
doesn't rewrite state, so `tofu.sh rekey <stack>` re-encrypts it (`state
pull | state push`, never touching disk) and skips a stack already on the
current key. `opentofu_rotates_the_passphrase` in `src/synth.rs` runs two
rotations with real OpenTofu. Wiring this into Infra Mint and the
workflows is `infra/docs/issues/iac-rotate-state-passphrase.md`; until then the
passphrase is rotated only after a leak, by hand.

## Changing a setting

Edit the construct or stack, run `mise run synth`, and commit the change to
`src/` and `out/` together. `mise run ci` checks that they match and that
`tofu validate` accepts the output.

## Adding a resource type

Add it to the `include` list in `terrars_<provider>.json`, run
`mise run bindings` (needs `terrars-generate` from `cargo install terrars`,
and `tofu`), and commit `src/tfschema/`. Generate only what is used: the
whole Cloudflare provider is 450,000 lines and adds a minute or two to CI
([spike note](../standards/docs/decisions/0007-terrars-spike.md)).

To move to a new provider version, change `version` in
`terrars_<provider>.json` and `AUTH0_PROVIDER_VERSION` (or its sibling) in
`src/tfschema/mod.rs`, regenerate, and update the hashes in
`out/<stack>/.terraform.lock.hcl` from the provider release's `SHA256SUMS`.
